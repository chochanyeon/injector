# 03. 개발 순서와 완료 기준

최종 갱신: 2026-11-16. [인덱스](00-index.md) · [현재 상태](02-status.md)

## 1. 순서표

아래는 확정 요구사항을 구현하기 위한 개발 계획 초안이다. 기능 추가 요청이나 설계 결정으로 순서가 바뀌면 이유를 남긴다. 번호는 유지하고 순서표를 갱신한다. 현재 다음 작업은 **T-010**이다.

| 순서 | ID | 작업 | 상태 | 선행 작업 |
|---|---|---|---|---|
| 01 | T-010 | 실행용 앱 등록 스키마 | 미착수 | 없음 |
| 02 | T-020 | 등록 로딩·검증·대상 프로젝트 지정 | 미착수 | T-010 |
| 03 | T-030 | 접속 정보 해석과 설정 주입 | 미착수 | T-020 |
| 04 | T-040 | DFS 실행 계획 | 미착수 | T-020, T-030 |
| 05 | T-050 | 실행·준비 상태 확인 | 미착수 | T-040 |
| 06 | T-060 | 대상 앱 실행 파이프라인 | 미착수 | T-030, T-050 |
| 07 | T-070 | 사용자 정의 호스트 이름 연결 | 미착수 | T-030, T-060 |
| 08 | T-080 | 의존성별 실제 실행·모의 대체 | 미착수 | T-040, T-050 |
| 09 | T-090 | 세션·실패 처리·종료 정책 | 미착수 | T-050, T-060 |
| 10 | T-100 | LLM 등록 초안의 검증·변환 | 미착수 | T-020, T-040 |
| 11 | T-110 | 다중 앱 통합 검증 | 미착수 | T-060~T-100 |
| 이후 | T-120 | IDE 실행 전 자동 준비 연동 | 후보 | T-110, D-01 결정 |

각 작업은 해당 기능의 의미 있는 검증까지 포함한다. T-110까지 테스트를 미루지 않는다. 최소 동작 파이프라인은 T-060에서 확인하고 나머지 작업으로 범위를 확장한다.

## 2. 작업 상세

### T-010 실행용 앱 등록 스키마

- 관련: R-08~R-11, 설계 15~16절, D-02~D-07.
- 시작: 현재 데모 설정과 LLM 등록 프로토콜을 비교해 실행에 필요한 정보와 조사용 정보를 분리한다.
- 산출물: `docs/05-registry-schema.md`에 버전, 앱 ID, 프로젝트 경로, 실행 모드, 접속점, 이름 해석, 의존 간선, 주입 참조, 준비 기준을 정의한다. 런타임 형식과 예시는 이 작업에서 결정한다.
- 완료 기준: 두 앱이 공통 인프라를 참조하는 다단계 예시와 실제·모의 대체 선택을 표현한다. 필수값·기본값·비밀값 참조·알 수 없는 값 처리·기존 POC 호환 범위를 명시한다.
- 검증: 각 필드의 출처와 사용처를 설명하고, 순환·누락 참조·충돌 예시를 표현할 수 있는지 검토한다. 구현을 시작하기 전에 미결정 선택의 이유를 기록한다.

### T-020 등록 로딩·검증·대상 프로젝트 지정

- 관련: R-01, R-08, D-03.
- 산출물: T-010 형식의 로더와 대상 프로젝트 선택 경로. 구체적인 CLI 인자는 스키마 설계 후 결정한다.
- 완료 기준: 데모 고정 경로 외 프로젝트를 읽고, 잘못된 형식·중복 ID·존재하지 않는 접속점·의존 참조를 명확히 알린다. 설정 해석만으로 서비스가 시작되지 않는다.
- 검증: 서로 다른 두 fixture, 상대 경로와 공백 경로, 잘못된 등록 입력을 검사한다. 기존 POC 동작의 유지 또는 이전 방법을 확인한다.

### T-030 접속 정보 해석과 설정 주입

- 관련: R-01, R-02, R-08, D-07.
- 산출물: 호출자 위치에 따른 접속 주소 계산과 VM 옵션·env 주입 결과.
- 완료 기준: 호스트 이름·바인딩·공개 포트·내부 포트를 구분한다. 공통·프로필·개인 설정을 지원할 범위와 충돌 우선순위를 결정하고, 최종값의 출처를 추적한다. 비밀값은 노출 없이 참조한다.
- 검증: 같은 접속점의 로컬 JVM·Docker 주소, 공백·특수문자, 중복 키, 미해결 참조, 로그의 비밀값 미노출을 검사한다.

### T-040 DFS 실행 계획

- 관련: R-06, R-09, 설계 15절.
- 산출물: 대상에서 도달 가능한 그래프와 결정적인 DFS 후위 실행 순서. 계획 단계에는 기동 부작용이 없다.
- 완료 기준: 하위 의존성이 먼저 나오고 공통 노드는 한 번 포함된다. 순환 경로와 충돌·누락을 자원 기동 전에 보고한다. 선택한 모드에 필요한 간선만 탐색한다.
- 검증: 직선·분기·공통 의존·자기 순환·다중 노드 순환·도달 불가능한 노드·모드별 하위 그래프를 검사한다.

### T-050 실행·준비 상태 확인

- 관련: R-03, R-04, R-09, D-05~D-06.
- 산출물: 계획에 따라 로컬 프로세스·Compose 자원을 준비하고 상태를 확인하는 실행 경로.
- 완료 기준: 하위 의존성 준비를 기다린 뒤 다음 노드를 실행한다. 프로세스 시작과 사용 준비를 구분하며, 시간 초과·종료를 감지한다. 생성 자원과 기존 자원의 소유권을 기록한다.
- 검증: 지연 준비, 시작 실패, 준비 시간 초과, 기존 포트 점유를 재현한다. 실패 시 그 자원에 의존하는 앱이 시작되지 않아야 한다.

### T-060 대상 앱 실행 파이프라인

- 관련: R-01~R-04, R-09~R-10, D-01.
- 산출물: 대상 선택 → 계획 검증 → 의존성 준비 → 설정 적용 → 대상 앱 실행을 연결한 흐름.
- 완료 기준: CLI·Docker 대상은 의존성 준비 후 시작한다. IntelliJ 대상은 전용 실행 구성을 준비하고 Debug 진입 시점을 명확히 한다. IDE 직접 자동 시작은 T-120과 구분한다.
- 검증: 대상 앱의 두 단계 이상 하위 의존성까지 순서대로 준비하고, 마지막 앱에 계산한 설정이 전달되는지 확인한다. IntelliJ 브레이크포인트도 별도로 확인한다.

### T-070 사용자 정의 호스트 이름 연결

- 관련: R-08, D-08.
- 시작: hosts·로컬 DNS 등 제공 방식, 적용 범위, 필요한 권한, 충돌·복원 정책을 결정한다.
- 완료 기준: `catalog.local.test.com` 같은 이름의 해석과 실제 호출이 함께 동작한다. 기존 사용자 매핑을 보존하고 도구가 만든 변경을 구별한다.
- 검증: 미등록 이름, 기존 매핑 충돌, 호출자 위치별 이름 해석을 확인한다. 실제 시스템 변경이 필요하면 적용 내용과 복원 방법을 먼저 구체화한다.

### T-080 의존성별 실제 실행·모의 대체

- 관련: R-05~R-06, D-04.
- 산출물: 전체 실제·전체 대역·혼합 구성을 선택한 그래프에 반영하는 기능.
- 완료 기준: 대역을 선택하면 실제 앱 전용 하위 의존성은 빠지고, 다른 앱이 필요로 하는 공통 자원은 유지된다. 주입 주소도 선택한 접속점을 따른다.
- 검증: 같은 대상 앱의 세 구성에서 실제 기동 노드와 호출 결과를 비교한다. WireMock 외 프로토콜 지원 범위를 임의로 확대하지 않는다.

### T-090 세션·실패 처리·종료 정책

- 관련: 설계 9절, D-06~D-08.
- 산출물: 세션 소유권·재사용·종료·실패 정리·데이터 보존 정책과 구현.
- 완료 기준: 기존 자원을 임의 종료하지 않고, 실패한 실행에서 생성한 자원을 식별한다. 공유 자원·포트 충돌·재실행과 종료 순서를 정의한다. 데이터 초기화는 명시적인 정책을 따른다.
- 검증: 부분 실패 후 재실행, 공유 자원 종료, 기존 프로세스 보존, 중단 후 복구를 확인한다. 범위에 포함한 데이터 보존 정책도 검증한다.

### T-100 LLM 등록 초안의 검증·변환

- 관련: R-11, 설계 16절.
- 산출물: 검토용 초안을 T-010의 실행 설정으로 변환하는 경로와 갱신한 등록 스킬.
- 완료 기준: 근거·제안·미확인 값을 구분하고 미확인 필수값을 실행 가능한 설정으로 승격하지 않는다. 기존 사용자 확정값을 보존한다. 변환만으로 앱·hosts 변경을 실행하지 않는다.
- 검증: 정상 초안, 근거 누락, 필수값 미확인, 순환·충돌, 기존 등록 갱신을 검사한다. 스킬 형식과 실제 모노레포 또는 fixture 조사 산출물도 검토한다.

### T-110 다중 앱 통합 검증

- 산출물: `examples/` 아래 분리된 다중 앱 데모와 최신 검증 기록.
- 완료 기준: 공통 DB를 쓰는 앱, 다른 앱의 API 의존성, 모의 대체, 사용자 정의 호스트, 실패 경로를 한 흐름으로 재현한다. 도구 코드를 바꾸지 않고 두 프로젝트 구성을 선택한다.
- 검증: 깨끗한 환경에서 재현 절차를 따라 기동·디버그·전환·정리를 수행하고 실제 결과와 제한을 04에 기록한다. 업무 모노레포가 없으면 범용성이 실제 업무에서 검증되었다고 표현하지 않는다.

### T-120 IDE 실행 전 자동 준비 연동

- 상태: 후보. 자동화 방향은 요청되었지만 연동 방식·제공 형태·착수 시점은 미정이다.
- 시작 조건: D-01 결정과 기본 실행 파이프라인 검증.
- 검토 범위: Run / Debug 전에 준비 작업 자동 호출, 취소·실패 전달, 재실행 시 중복 기동 방지. 플러그인을 필수로 가정하지 않는다.
- 완료 기준: 사용자가 선택한 IDE 흐름에서 의존성 준비 실패 시 대상 앱 실행이 진행되지 않는 것을 확인한다.

## 3. 범위가 확정되지 않은 항목

DB 스키마·초기 데이터·Kafka 토픽 초기화, 비HTTP 모의 대체 엔진, 외부 통신 강제 차단, 모든 언어·IDE 지원은 아직 확정 구현 범위가 아니다. 필요할 때 R/D-ID와 연결해 결정하고 새 T-ID를 부여한다.
