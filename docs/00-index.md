# 00. 개발 문서 인덱스

최종 갱신: 2026-11-16. 이 파일은 대화 기록 없이 Injector 개발을 재개하기 위한 시작점이다.

## 1. 읽는 순서

| 순서 | 문서 | 확인할 내용 |
|---|---|---|
| 00 | 이 문서 | 재개 절차, 문서별 책임 |
| 01 | [설계](01-design.md) | 확정 요구사항 R-ID, 미결정 사항 D-ID, 목표 동작 |
| 02 | [개발 현황](02-status.md) | 구현·미구현·검증 범위, 코드 위치, 현재 인계 상태 |
| 03 | [개발 순서](03-roadmap.md) | T-ID별 의존 작업·완료 기준·검증 방법 |
| 04 | [검증 기록](04-validation.md) | 실제 수행한 검증과 환경·한계 |

실행 방법은 [루트 README](../README.md), LLM 등록 작업은 [등록 스킬](../skills/injector-register-monorepo/SKILL.md)과 [프로토콜](../skills/injector-register-monorepo/references/registration-protocol.md)을 참고한다.

## 2. 지금 재개한다면

**다음 작업은 T-010: 실행용 앱 등록 스키마 설계다.** 아직 구현하지 않았다. [작업 상세](03-roadmap.md#t-010-실행용-앱-등록-스키마)에서 시작한다.

1. `git status --short --branch`와 최근 커밋을 확인한다. 미커밋 변경이 있으면 작성 주체와 작업 범위를 먼저 파악한다.
2. 01 → 02 → 03 순서로 읽고 현재 요청과 충돌하는 내용이 없는지 확인한다. 최신 사용자 지시가 문서보다 우선한다.
3. 진행할 T-ID와 완료 기준을 정한다. 선행 작업이 미완료라면 누락된 설계를 먼저 해결한다.
4. `python -m unittest discover -s tests -v`로 기본 상태를 확인한다. 현재 예상 결과는 2개 테스트 통과다. 테스트가 늘어나면 이 설명도 갱신한다.
5. 선택한 작업만 구현·검증하고 02의 상태, 03의 작업 상태, 04의 검증 근거를 갱신한다.
6. 커밋·푸시 후 로컬과 원격의 동기화를 확인한다. 다음 작업과 남은 문제를 02의 인계란에 남긴다.

실행 중인 컨테이너, 열려 있는 IntelliJ 창, 설치된 JDK 이름은 이전 대화의 상태를 가정하지 말고 다시 확인한다. 기본 단위 테스트에는 Docker나 IntelliJ가 필요하지 않다.

## 3. 상태와 기록 규칙

| 상태 | 의미 |
|---|---|
| 완료 | 해당 작업 범위의 산출물과 검증 근거가 존재함 |
| 부분 구현 | 일부 경로만 동작하며 제한 사항이 명시됨 |
| 진행 중 | 현재 작업 중이며 남은 내용·재개 지점이 기록됨 |
| 미착수 | 아직 구현하지 않음 |
| 후보 | 필요성과 범위가 확정되지 않음 |

- 요구 방향은 01, 현재 동작은 02, 앞으로 할 일은 03, 검증 사실은 04를 기준으로 삼는다. 문서끼리 다른 상태를 쓰지 않는다.
- 설계가 존재한다는 이유로 구현 완료라고 표시하지 않는다. 단위 테스트와 수동 통합 검증도 구분한다.
- 문서 번호와 R/D/T-ID는 유지한다. 항목을 삭제·변경할 때는 대체한 항목이나 이유를 남긴다.
- 새 문서는 역할이 기존 문서와 겹치지 않을 때 번호를 붙여 추가하고 이 인덱스에 연결한다.
- 커밋 해시는 선택적인 근거다. 상태 갱신 커밋 자신의 해시를 다시 적기 위한 추가 커밋은 만들지 않는다. 정확한 최신 이력은 `git log`로 확인한다.

## 4. 문서 갱신 시 확인

관련 코드·파일 경로와 상대 링크가 유효한지, 다음 작업이 실제로 미완료인지 확인한다. 문서에 적힌 명령은 현재 디렉터리 구조에서 실행할 수 있어야 한다. 테스트 결과를 재사용하면 검증한 시점을 명시하고 이번에 다시 실행한 것처럼 쓰지 않는다.
