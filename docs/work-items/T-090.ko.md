## 1. 설계

- 관련: [전체 설계](../design.ko.md) 9절, D-06~D-08.
- 완료 기준: 기존 자원을 임의 종료하지 않고, 실패한 실행에서 생성한 자원을 식별한다. 공유 자원·포트 충돌·재실행과 종료 순서를 정의한다. 데이터 초기화는 명시적인 정책을 따른다.
- 재준비 전에 실행 명령, IntelliJ 산출물, 예정된 TCP 접속점과 Docker 서비스 충돌을 검사한다. 이전 세션이 실제로 사용하는 리스너는 재준비 대상 포트로 허용한다. 다른 리스너와 충돌하면 기존 세션과 설정을 보존한다. 종료 직후에도 포트를 다시 검사한다.
- 의존성 준비가 끝나면 IntelliJ XML과 Spring YAML을 갱신한다. 전환 뒤 실패하면 이번에 띄운 자원을 정리하고 이전 IDE 설정을 보존한다. 이전 구성을 다시 시작하려면 환경 참조를 포함한 입력을 확인해 명시적으로 준비한다.
- 새 Compose 세션은 시작한 Docker 엔진에서 종료한다. 공유 서비스는 external로 등록한다. 종료 시 볼륨과 네트워크를 보존한다.
- 런처 시작 전에 실행 단위의 식별자를 기록한다. Windows에서는 명명된 Job Object로 런처가 종료되거나 별도 `stop`이 호출될 때 자식을 정리한다. macOS에서는 독립 프로세스 그룹에서 런처와 자식을 관리한다. 자체 세션으로 분리되는 데몬은 `compose` 또는 `external`로 등록한다. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)
- `process` 명령에 경로가 있으면 노드의 `workingDirectory`를 기준으로 해석한다. 명령 이름만 있으면 실행 환경의 `PATH`와 Windows `PATHEXT`를 사용한다. 해석한 절대 경로를 실행에도 사용한다.

## 2. 개발

- [runtime.py](../../injector_core/runtime.py)에 세션 전환 전 포트 소유권 확인, 상대 경로 명령 해석과 프로세스 정리를 추가했다. 구버전 세션의 PID·생성 시각 기반 종료도 지원한다.
- [process_runner.py](../../injector_core/process_runner.py)가 세션 기록이 저장된 뒤 런처를 시작하고 자식 프로세스의 수명을 관리한다.
- [rendering.py](../../injector_core/rendering.py)에서 IntelliJ 설정의 생성과 파일 반영을 분리했다. 파일별로 교체하며 XML 교체 실패 시 먼저 반영한 YAML을 복원한다.
- 자원마다 정리 진행을 세션에 저장한다. Docker 오류는 작업 단계와 알려진 오류 종류를 표시하며 원본 출력은 제외한다.

## 3. 검증

- Windows에서 `python -m unittest discover -s tests` 107개를 통과했다. 실제 WireMock Vault와 Spring Boot JAR을 함께 검증했다. 새 회귀 테스트는 외부 포트 충돌 시 이전 세션·XML 보존, 기동 실패 시 기존 XML·Spring YAML 보존, 런처 종료 후 자식 정리, 공백이 있는 모듈의 상대 경로 실행을 확인한다.
- Linux 컨테이너의 Python 3.10에서 런타임 테스트 16개를 모두 통과했다.
- Windows에서 `prepare`와 `stop`을 별도 CLI 프로세스로 실행해, 준비 명령이 종료된 뒤에도 서비스가 유지되고 종료 명령이 두 프로세스 트리를 정리하는 것을 확인했다.
- Windows에서 데모 임시 사본으로 Compose 재준비와 종료를 확인했다. 생성된 `.run`의 환경 변수·VM 옵션으로 Java 데모를 띄우고 WireMock을 호출했다. 동일 포트로 재준비하고 관리 대상 컨테이너가 모두 종료되는 것을 확인했다.
- 실제 macOS 기동, IntelliJ의 Debug 버튼, 업무 모노레포 도그푸딩은 후속 검증에 포함한다.
