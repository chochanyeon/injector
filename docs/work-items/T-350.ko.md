# T-350 · 재현 가능한 체크아웃 증거로 수정 검증

**[English](T-350.md)** · 한국어 · [작업 인덱스](../index.ko.md)

## 설계

에이전트가 명령 하나로 두 워크트리를 기동하고 체크아웃을 재현한 뒤, 검토할 수 있는 증거를 남긴다. 쇼핑몰 예제는 매번 같은 초기 데이터를 제공한다. 시나리오는 Injector가 선택한 그래프의 읽기 전용 HTTP 조회로 초기 상태, 기대 응답, 최종 상태를 정의한다. 기존 Loki 수집기는 HTTP와 Kafka 흐름을 기록한다. Walden Yan 발표의 검증 방식에 해당한다. [AI Engineer CODE 2026 발표](https://ai.engineer/code/2026/talks/walden-yan)

- 초기 상태가 다르면 증거를 남기고 상태를 변경하는 요청을 건너뛴다.
- 두 워크트리가 같은 방식으로 동작해도 기대 결과를 어겼다면 실패로 판정한다.
- 수정 검증은 기준 쪽에서 지정한 실패가 재현되고 후보의 모든 검사와 필수 이벤트가 확인되어야 통과한다.
- 실행이 중단되면 보고서에 노드별 기동 단계와 생성된 기록을 남긴다.
- 기존 시나리오도 계속 실행할 수 있다.

## 개발

1. 요청 흐름 시나리오에 `expect`와 `stateChecks`를 추가했다. 상태 검사는 등록된 루프백 HTTP 엔드포인트에 GET을 보낸다. `before` 검사에 실패하면 기록을 남기고 시나리오 요청을 건너뛴다. `after` 검사는 비동기 결과를 기다릴 수 있다. 지정한 값만 기록한다.
2. `compare-worktrees`와 `compare-http`에 `--prove-fix CHECK_ID`를 추가했다. 회귀 비교는 양쪽의 검사가 통과하고 관측이 일치해야 한다. 수정 검증은 기준에서 지정한 실패를 재현하고 후보에서 모든 증거를 확보해야 한다. 종료 코드 0·1·2는 각각 `PASS`·`FAIL`·`INCONCLUSIVE`를 뜻한다.
3. 관측 파일 옆에 `report.json`을 작성한다. 시나리오 해시, 워크트리 경로, 노드별 실행 단계와 증거를 담는다. 비교 도중 기동 또는 실행이 실패하면 실패 사유와 이미 끝난 쪽의 기록을 남긴다.
4. 쇼핑몰 `mock` 시나리오에서 초기 재고, 주문 저장과 금액, 최종 재고, Kafka 소비 후 배송 상태를 확인한다. PostgreSQL과 Redis 상태는 앱의 GET 엔드포인트로 확인한다.

## 검증

- Windows의 요청 흐름·워크트리 테스트에서 초기 재고가 다르면 주문을 보내지 않고, 양쪽 결과가 같아도 기대값이 다르면 실패하고, 상태 조회가 불가능하면 `INCONCLUSIVE`를 반환하는 것을 확인했다. 앱이 준비 전에 종료될 때는 보고서와 기존 버전 기록이 남았다.
- Docker Desktop과 JVM으로 쇼핑몰을 띄웠다. 동일한 두 복사본은 검사 여섯 개를 모두 통과했고 HTTP·Kafka 이벤트 열 개를 남겼다. 대역의 단가를 999에서 998로 바꾸자 응답은 HTTP `201`이었지만 응답과 저장된 주문 모두 합계가 1,996센트였다. 이 기록을 자기 자신과 비교한 회귀 검사는 `FAIL`이었다. 이를 정상 버전 기록과 `--prove-fix response`로 비교했을 때는 `PASS`였다.
- 실제 `compare-worktrees --prove-fix response` 명령으로 두 복사본을 차례로 띄웠다. 전체 판정은 `PASS`였고 보고서에 양쪽의 준비 완료 노드 각 열한 개, 기준의 실패 두 건, 후보의 통과 여섯 건이 남았다.
- Windows 회귀 재실행에서 Spring Boot와 WireMock Vault를 포함한 테스트 144개가 통과했다. 쇼핑몰 통합 테스트 두 개는 최초 실행에서 통과했다. 기존 기본 레지스트리 세션 테스트의 프로세스 ID 검사가 최초 실행에서 한 번 실패했고 단독 실행과 회귀 재실행에서 통과했다. Injector가 기동한 Docker 컨테이너는 모두 정리됐다.
