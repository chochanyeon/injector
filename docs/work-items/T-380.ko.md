# T-380 · 입력 대기 없는 등록·검증 자동화

**[English](T-380.md)** · 한국어 · [작업 인덱스](../index.ko.md)

## 설계

LLM이 검토된 레지스트리, 시나리오의 기대 동작, 워크트리 경로를 사용해 CLI에서 로컬 검증을 끝낸다. 최초 등록에서는 코드 근거를 수집하고 누락된 설정이나 검토할 결정을 표시한다. 반복 실행은 승인된 입력으로 사전 점검, 앱과 의존성 기동, 실패 재현, 후보와 관련 동작 검증, 자원 정리까지 수행한다. 웹 화면도 같은 검증·실행 로직을 사용한다.

- 사전 점검은 앱을 시작하기 전에 모든 항목을 확인한다. 대상 시나리오나 노드, 누락된 입력 또는 실패한 검사 항목을 구조화해 반환한다.
- 실행은 판정, 종료 코드, 증거 파일 경로와 함께 입력 오류·기동 실패·동작 차이·정리 실패를 구분한 버전 있는 결과를 남긴다. LLM은 이 결과로 다음 조치를 판단할 수 있다.
- 새 에이전트가 문서화된 조건에 따라 등록된 대상 프로젝트를 실행하고, 화면 조작 없이 검증 보고서를 생성할 수 있다. 기대하는 업무 동작과 필요한 비밀 값은 검토된 입력을 사용한다.

## 개발

- [스위트 계획](../../verifier/worktree_suite.py)은 워크트리 두 개와 등록된 모든 시나리오를 검사한다. `check-suite`는 `READY` 또는 `BLOCKED`, 해당 종료 코드, 진단 위치를 버전 1 JSON으로 반환한다. `verify-suite`도 같은 사전 점검을 사용하며, 실행이 막히면 해당 JSON을 반환한다.
- [Injector](../../injector_core/runtime.py)는 런타임 파일을 만들지 않고 활성 세션, 필요한 설정, 호스트 해석, Compose 구성과 엔진, 사용 중인 포트를 검사한다. 실행 시 세션과 기동 조건을 다시 확인한다. 환경변수가 빠진 경우 이름만 표시한다.
- LLM은 시나리오 번호, 워크트리 구분, 노드로 장애 위치를 찾을 수 있다. 소스 빌드와 초기 데이터 준비는 대상 프로젝트의 절차를 따른다. [등록 절차](T-340.ko.md) · [스위트 실행](T-360.ko.md) · [Verifier 사용법](../../verifier/README.ko.md#스위트-실행)

## 검증

- Windows 프로세스 테스트에서 정상 스위트, 후순위 시나리오의 잘못된 수정 검사 ID, `check-suite`와 `verify-suite`의 같은 차단 결과, 두 워크트리 각각의 환경변수·포트 오류를 검증했다. 보고서에 실제 설정값이 들어가지 않았고 런타임·출력 파일도 쓰지 않았다.
- Windows 회귀 테스트는 Spring Boot를 포함해 143개가 통과했고 선택 실행 테스트 8개는 건너뛰었다. 별도로 Docker와 JVM을 실제로 띄워 CLI를 통한 쇼핑몰 스위트 두 항목이 공통 사전 점검부터 실행까지 통과함을 확인했다.

## 재개 지점

기동, 관측, 정리 실패를 기계가 구분할 수 있게 결과를 구조화한다. 등록된 업무 모노레포와 macOS에서 CLI를 검증한다.
