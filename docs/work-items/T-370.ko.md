# T-370 · 필수·금지 이벤트 발생 횟수 검증

**[English](T-370.md)** · 한국어 · [작업 인덱스](../index.ko.md)

## 설계

시나리오가 같은 요청에 연결된 이벤트의 기대 횟수를 지정한다. 거절된 요청에는 Kafka 이벤트 0회, 정상 주문에는 발행과 소비 각 1회를 요구할 수 있다. 기존 이벤트 조건을 사용하고, 지정한 시간 동안 관측이 안정된 뒤 횟수를 판정한다.

- 양쪽에서 같은 횟수를 보이더라도 기대 횟수와 다르면 실패한다.
- 관측 증거가 불완전하거나 조회가 불가능하면 횟수 검사는 `INCONCLUSIVE`다.
- 기존 시나리오는 기존 방식으로 요청 흐름을 비교한다.

## 개발

- [시나리오·기록 스키마](../../schemas/http-observation-v1.schema.json)에 `trace.eventCounts`와 `trace.settleSeconds`를 추가했다. 각 횟수 검사에는 고유한 ID와 이벤트 조건을 둔다. 필수 이벤트를 0회로 지정하면 사전 검증에서 오류를 표시한다.
- [Loki 수집기](../../injector_core/trace_observation.py)는 기록이 바뀌거나 조회가 끊기면 안정화 시간을 다시 센다. 기대 횟수, 관측 횟수, 판정을 기록하며 검사 ID를 `proveFix`에 지정할 수도 있다.
- [정상 주문](../../examples/demo/monorepo/scenarios/checkout-evidence.json)은 발행과 소비가 각 1회여야 한다. [거절된 주문](../../examples/demo/monorepo/scenarios/checkout-invalid-quantity.json)은 각 0회여야 한다.

## 검증

- 중복 발행, 기존 0.75초 기준 이후에 도착한 발행, 관측 누락, 같은 이벤트를 요구하면서 0회로 설정한 시나리오를 테스트했다. 공통 스키마는 JSON Schema 검사를 통과했다.
- Windows Docker와 JVM으로 실행한 실제 스위트는 두 항목 모두 통과했다. 두 워크트리에서 정상 주문의 발행·소비는 각 1회, 거절된 주문은 각 0회였다. Markdown 요약에서 상세 보고서 두 개와 기록 네 개를 열 수 있다. Injector가 기동한 컨테이너는 모두 정리됐다.
- Windows 회귀 테스트는 Spring Boot와 WireMock Vault를 포함해 147개가 통과했다. 별도 실행 옵션이 필요한 기존 쇼핑몰 테스트 두 개는 이 실행에서 건너뛰었다. 새 Docker 동작은 실제 쇼핑몰 스위트로 검증했다.

## 재개 지점

업무 모노레포의 초기 데이터와 실제 로그 지연을 반영해 스위트를 검증한다. [T-380](T-380.ko.md)에서 입력 대기 없는 실행 흐름을 정한다. 로컬 웹도 같은 흐름을 사용할 수 있다.
