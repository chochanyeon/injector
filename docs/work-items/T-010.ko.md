## 1. 설계

관련: R-08~R-11, 공통 설계 15~16절, D-02~D-07. 초기 실행 모델은 JVM·IntelliJ·로컬 프로세스·Compose 중심으로 정의한다. 언어 전체를 지원한다는 의미는 아니다.

### 1.1. 형식 선택과 경계

실행용 형식은 JSON, 버전은 `schemaVersion: "1.0"`, 구조 계약은 JSON Schema Draft 2020-12로 선택했다. 기존 POC가 JSON을 사용하고, 직접 구조 검사 코드를 중복 작성하지 않고 표준 검증기를 사용할 수 있기 때문이다. Python 검증기는 `jsonschema==4.26.0`으로 고정했다. 제품 언어·IDE 제공 형태 전체를 확정한 결정은 아니다.

조사용 `draftVersion: "0.1"`과 기존 데모의 `project.json`은 별도 계약이다. 자동 승격·자동 마이그레이션하지 않는다. 기존 CLI 동작은 유지하고, 실행용 등록을 다루는 경로는 T-020부터 추가한다.

### 1.2. 모델

| 위치 | 내용과 사용처 |
|---|---|
| 루트 `schemaVersion` | 정확히 `1.0`. 미지원 버전을 추정 해석하지 않음 |
| `nodes[]` | `id`, `kind`, `variants`. ID는 소문자·숫자·하이픈으로 시작 문자는 소문자 |
| `kind` | `application` 또는 `infrastructure` |
| `variants` | 논리적으로 같은 앱의 `real`, `mock` 등 이름 있는 실행 정의. 실제 이름은 임의 ID |
| variant `execution` | `process`, `intellij`, `compose`, `external` 중 하나 |
| variant `endpoints` | 노드 내 이름으로 식별하는 접속점. 프로토콜·바인딩·호스트/컨테이너별 호출 주소 |
| variant `dependencies` | 이 실행 정의에 필요한 노드 ID 배열. 순서 유지·배열 내 중복 금지 |
| variant `readiness` | HTTP 경로·접속점, TCP 접속점, Compose healthcheck 중 하나와 시간 제한 |
| variant `injections` | 환경변수 또는 VM 시스템 속성 키에 의존 노드의 접속점 정보를 연결 |
| `profiles` | 대상 앱 `targets`, 노드별 variant `selections`, 선택적 `overrides` |
| `defaults` | 공통 env·VM 옵션·VM 시스템 속성. 생략 시 빈 설정 |
| `nameMappings` | 이름·해석 주소·`hosts` 또는 기존 `external` 해석 방식의 선언. 실제 적용은 T-070 |

노드 ID와 접속점 ID는 논리 식별자다. `catalog`는 프로필에 따라 실제 Catalog 또는 WireMock에 연결되며, 각 variant는 자기 하위 의존성을 갖는다. 의존성을 트리로 복제하지 않으므로 공통 DB는 하나의 ID로 공유한다.

각 프로필은 실행할 대상과 필요한 노드의 variant를 명시한다. variant 기본값이나 첫 프로필 자동 선택은 없다. 선택된 그래프에서 필요한 노드의 선택이 없으면 오류다. 사용되지 않는 variant의 실행은 요구하지 않는다.

### 1.3. 실행과 주소

- `process`: shell 문자열 대신 `command` 인자 배열과 `workingDirectory`.
- `intellij`: `projectPath`, `module`, `mainClass`. 전용 XML 생성에 사용.
- `compose`: `file`, `service`, `projectName`. 프로젝트명을 자동 추측하지 않음.
- `external`: 도구가 새 프로세스를 만들지 않는 기존 자원. 준비 기준은 여전히 필요.
- 경로는 등록 대상 프로젝트 루트 기준이다. 소스·Compose 파일 존재 여부는 실행 단계에서 확인하고, 상대 경로의 루트 이탈 검사는 T-020에서 한다.
- `bind`는 수신 주소·내부 포트다. `addresses.host`와 `addresses.container`는 호출자가 쓰는 주소·포트다. 호출자별 이름 해석을 함께 해결한 것으로 간주하지 않는다.
- 주소의 `scheme`과 `path`는 URL 조립에 사용한다. TCP·DB 접속점에는 생략할 수 있다. `url` 주입은 scheme이 있는 주소에만 허용할 예정이며 T-030에서 해석한다.
- 주입의 `source`는 `node`, `endpoint`, `context`, `component`를 가진 구조화 참조다. component는 `url`, `host`, `port`다. 임의 문자열 템플릿을 평가하지 않는다.

### 1.4. 합성·미확인 값·비밀값

설정 합성 순서는 공통 defaults → 선택 variant → 프로필의 해당 노드 override다. env와 vmProperties는 뒤의 값이 덮어쓰고 vmOptions는 순서대로 연결한다. 개인별 값은 `{"fromEnv":"LOCAL_DB_PASSWORD"}` 참조로 공급한다. 별도 개인 설정 파일은 v1.0 범위에서 추가하지 않는다.

`-Xmx` 등 JVM 실행 옵션은 `vmOptions`, `-Dkey=value`는 `vmProperties`에 둔다. raw VM 옵션에 `-D`를 넣으면 구조 검사에서 거부한다. 주입 규칙과 수동 지정 키의 충돌 정책·최종값 출처 추적은 T-030에서 구현한다.

실행 필수값의 `null`, 알 수 없는 속성, 미지원 버전을 거부한다. 미확인 값은 조사 초안에 남기고 실행용 등록으로 변환하지 않는다. 생략 가능한 설정은 빈 설정/배열로 해석하며 JSON Schema의 default 삽입 기능에 의존하지 않는다. 비밀값은 환경변수 참조로 관리하고 실제 값을 저장소에 넣지 않는다. 문자열 literal을 기술적으로 금지하는 것은 아니므로 자격증명 여부를 자동 판정한다고 설명하지 않는다.

### 1.5. 구조 검사와 의미 검사

JSON Schema는 자료형·필수 필드·범위·실행별 필드를 검사한다. 노드 ID 중복, 간선 대상 존재, 선택 variant, 주입·준비 접속점 참조는 T-020의 의미 검사다. 순환·실행 순서는 T-040, 포트 충돌·이름 해석·자원 수명은 관련 후속 작업에서 처리한다. 순환 그래프도 자료 구조로 표현할 수 있지만 실행을 허용한다는 의미는 아니다.

## 3. 검증

2026-11-17에 `python -m unittest discover -s tests -v`를 실행해 기존 2개와 스키마 8개, 총 10개 통과를 확인했다. `Draft202012Validator.check_schema`로 스키마 자체도 검증했다.

확인한 조건은 정상 예시, 조사 초안·레거시 형식 거부, 버전·오타 필드 거부, null 거부, 잘못된 포트, 실행별 필수값, raw -D 거부, 빈 비밀값 참조 거부다. 노드 간 참조·실제 실행·DNS는 이 작업의 검증 범위가 아니다.

참고: [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core), [검증기 공식 문서](https://python-jsonschema.readthedocs.io/en/stable/validate/).
