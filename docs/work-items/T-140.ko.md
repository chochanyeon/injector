## 1. 설계

관련: R-14. 업무 설정이 많아지는 경우 외부 YAML로 공급하고, JVM 플래그와 System.getProperty 전용 값은 VM 인자로 유지한다. 서비스별 원본 설정을 AI가 근거와 함께 등록할 수 있도록 가이드를 제공한다. 사용자 요청으로 T-050 전에 우선 처리했다.

### 1.1. 스키마와 채널

기존 v1.0 계약은 수정하지 않고 v1.1을 추가했다. 로더는 schemaVersion에 따라 로컬 스키마를 선택하고 미지원 버전은 거부한다. v1.1의 defaults·variant·profile override에 springProperties를 추가하고, injections에는 springProperty 채널을 추가했다.

vmOptions는 JVM 플래그 배열, vmProperties는 이름 있는 -D 시스템 속성, env는 환경변수, springProperties는 Spring property 이름과 YAML 값이다. Spring 값은 문자열·숫자·boolean·리스트·맵과 fromEnv 참조를 지원한다. null은 미확인 값으로 취급해 실행 등록에서 거부한다.

합성은 기존 defaults → variant → profile override 순서를 따른다. Spring 값도 같은 최상위 키를 뒤의 값으로 교체하며 배열·맵을 자동 deep merge하지 않는다. 겹치는 dotted key나 flatten 결과의 중복을 거부한다. env·VM 속성과 같은 leaf를 지정해 YAML을 가리는 경우도 검사한다. 모든 relaxed-binding 별칭·상속 환경·프로그램 인자까지 분석하는 기능은 아니다.

### 1.2. 생성과 실행 경계

`render --project <root> --profile <name> --node <id>`가 검증된 IntelliJ 실행 정의를 사용한다. 생성물은 root/.local/injector/profile/node/spring-overrides.yml과 앱 projectPath/.run/Injector-profile-node.run.xml이다. 원본 application YAML은 변경하지 않는다. XML에 기존 VM 값과 file URI 형태의 spring.config.additional-location을 넣는다.

Spring fromEnv는 실제 값을 파일에 쓰지 않고 ${ENV_NAME} placeholder로 남긴다. 실제 앱 환경이 값을 공급해야 한다. 현재 env·vmProperties의 fromEnv 값을 XML에 복사하는 경로는 거부하며, 이 런타임 전달은 T-050·T-060 이후에 연결한다. literal에 실제 자격증명을 넣어도 자동 판정할 수 있는 것은 아니므로 실제 자격증명은 등록에 넣지 않는다.

기존 additional-location과 충돌하면 자동 교체하지 않는다. spring.config.*와 active/default/include 프로필 선택은 생성 YAML이 아닌 VM 속성·환경변수에 둔다. opaque SPRING_APPLICATION_JSON도 이 render와 결합하지 않는다. 단순히 환경변수를 다른 이름으로 바꿔 우선순위를 회피하지 않고 소스를 정리해야 한다.

현재 생성은 IntelliJ 타입에 한정한다. Compose의 YAML 마운트와 컨테이너 경로 변환·앱 자동 기동은 미구현이다. 생성 경로의 프로젝트 이탈·심볼릭 링크를 거부하고, 해당 생성 경로만 덮어쓴다. 다른 레포에 적용할 때도 생성 경로를 Git에서 제외해야 한다.

### 1.3. AI의 레포 탐색·등록 관리

등록 스킬을 조사 초안 모드와 검토된 실행 registry 관리 모드로 구분했다. 읽는 코드·profile YAML·실행 인자·환경변수를 추적해 값의 채널을 판단하고 파일:줄 근거를 findings에 남긴다. 직접 YAML 파싱을 Spring 설정 바인딩으로 오인하거나, System.getProperty 전용 값을 YAML로 옮기지 않는다.

AI는 Injector의 실제 schema·로더·완료 작업을 확인하고 지원하는 필드로 등록을 갱신한다. 단일 registry.json 로더에 미구현 include 필드를 만들어 넣지 않는다. 기존 ID·프로필·사용자 확정값을 보존하며, 미확인 필수값은 실행용 등록에 추측으로 채우지 않는다. 필요 시 초안에 남긴다. validate·plan·resolve·render 성공을 앱 실행 성공으로 보고하지 않는다.

## 2. 개발

- [v1.1 스키마](../../schemas/registry-v1.1.schema.json), [로더](../../injector_core/registry.py): 버전별 구조 검사.
- [설정 해석](../../injector_core/resolution.py): 타입 보존 Spring 값·주소 주입·환경 참조·출처·충돌 검사.
- [rendering.py](../../injector_core/rendering.py): YAML·IntelliJ XML 생성 및 관리 경로·출력 보호.
- [CLI](../../injector.py): render 명령. 기존 데모·Vault·v1.0 경로 유지.
- [Spring 예제](../../examples/spring-config/): Boot 3.5.16·JDK 17 대상의 실제 HTTP 검증 앱과 registry.
- [단위 검사](../../tests/test_spring_rendering.py), [실앱 검사](../../tests/test_spring_boot_integration.py).
- [AI 가이드](../../skills/injector-register-monorepo/references/runtime-registry-guide.ko.md): 실제 계약 확인, 채널 선택, 근거·갱신·무기동 검증 힌트.

PyYAML 6.0.3 safe_dump를 사용한다. 임의 YAML 태그·코드를 생성하거나 실행하지 않는다. 원본 YAML의 자동 스캔·자동 변환 엔진을 구현한 것은 아니며 LLM이 탐색할 절차를 문서화했다.

## 3. 검증

2026-11-17에 샘플을 Maven으로 빌드한 후 실제 JDK 25 실행 파일로 Boot 3.5.16 앱을 띄웠다. 원본 프로필 YAML보다 생성 YAML이 적용되고 리스트도 바뀌며, VM 전용 값은 System.getProperty로 읽히는 것을 HTTP 응답으로 확인했다. YAML 값이 시스템 속성으로 자동 등록되지 않는 것, ${PROBE_SECRET}이 앱 환경에서 해석되는 것도 확인했다. 테스트 앱은 임시 폴더·별도 포트에서 시작하고 종료했다.

Spring JAR·JDK 경로와 Vault 통합 URL을 지정해 `python -m unittest discover -s tests -q`를 실행했고 **총 74개가 통과**했다. T-140 단위 검증 13개와 실앱 통합 1개를 추가했다. 기본 실행은 68개 수행·6개 통합 skip이다.

확인한 항목: v1.0/1.1 구분, typed list/map·한글·인용부호, 원본 파일 보존, 주소의 Spring 키 주입, 키 중복·부트스트랩 충돌, 생성 경로·실행 타입 제한, 서비스별 파일 분리, 실제 비밀값 미저장·redacted 출력, 무기동 render.

`render --project examples/spring-config --profile local --node spring-probe`도 실행했다. IntelliJ UI에서 새 구성을 Debug한 것은 아니며, 생성한 설정의 동일 JVM 인자로 실제 앱을 실행해 검증했다. Docker 마운트·회사 앱·다른 Spring 버전은 미검증이다. AI 가이드를 실제 회사 모노레포에서 수행한 행동 검증도 아직 없다.

참고: [Spring Boot 3.5 외부 설정](https://docs.spring.io/spring-boot/3.5/reference/features/external-config.html), [PyYAML 문서](https://pyyaml.org/wiki/PyYAMLDocumentation.html).
