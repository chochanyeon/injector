# T-340. Search for dependency evidence during monorepo registration

**English** · [한국어](T-340.ko.md)

[Work index](../index.md) · Prerequisites T-005 and T-320

## Design

Use a read-only search to gather common JVM and Spring dependency signals before investigating individual connections. Let a repeated repository-specific client pattern be added to the same search. Require caller, effective launch configuration, and provider evidence before promoting an edge into the registry.

Verify the helper on the shop demo and a fixture with an ambiguous provider, ignored paths, and a custom wrapper. Verify the installed skill copy and its links.

## Development

- The bundled Python search scans selected Java, Kotlin, YAML, and properties files. It emits relative paths, line numbers, and rules. Repeatable custom source patterns cover repository-specific clients.
- Both skill entrypoints and discovery guides start with the search and then trace caller, effective configuration, and provider evidence. The draft protocol keeps the scan scope, rules, remaining candidates, and next point to inspect in findings.

## Verification

- On Windows, the shop's shared HTTP wrapper rule found the locations for all six app-to-app HTTP calls. The source lines identified their targets. The DB wrapper produced a connection candidate while two PostgreSQL instances remained possible until the effective setting was reviewed.
- A temporary fixture checked scope restriction, overlapping scopes, Java and Kotlin search, build and test exclusions, candidate line numbers, omitted values, and unchanged inputs. The four registration regression tests passed.
- The skill validator and local references passed. Seven updated files were checked against the Windows installed copy, and the installed helper found both Orders HTTP calls.
