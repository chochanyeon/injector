## 1. 설계

LLM이 모노레포에서 앱·접속점·호스트·포트·주입 키·전이적 의존성을 조사하고, 근거와 미확인 사항을 포함한 등록 초안을 작성하도록 돕는다. 파일·줄 근거, 추론, 로컬 변경 제안을 구분하고 비밀값은 복사하지 않는다.

등록 초안은 실행용 설정과 분리한다. 조사 작업 자체가 앱 실행·hosts/DNS 변경·실제 등록 적용을 수행하는 것은 아니다. 실행용 변환은 T-100으로 분리했다.

최초 적용은 실행 후보 목록 → 대상 앱과 인프라 → 앱 간 연결 순서로 조사한다. 대상 앱 파일 하나를 기준으로 하위 의존성까지 등록하고 검증한 뒤 범위를 넓힌다. Spring 설정 조사는 실행 방식마다 파일·환경·코드의 근거를 대조한다.

일부 범위를 최초 등록할 때는 근거가 갖춰진 실행 방식 하나, 선택한 하위 그래프의 근거, 아직 막힌 입력의 기록을 완료 기준으로 삼는다. 실행용 등록은 필수 미확인 사항을 해결한 뒤 작성한다. 구조·계획 검증과 실제 설정 해석의 근거를 구분한다.

## 3. 검증

2026-11-16에 스킬 형식 검사, 예시 JSON 파싱, 노드·접속점·주입 참조 및 근거 필드 JSON Pointer의 유효성을 확인했다.

최초 등록 문서 추가 후 `python -X utf8 .../quick_validate.py skills/injector-register-monorepo`와 스킬 내부 상대 링크 검사를 통과했다. 데모에서 `validate`와 앱 대상 `plan`을 실행해 Catalog를 실제 앱으로 바꿀 때 PostgreSQL이 계획에 추가되는 것을 확인했다. Spring 예제는 소스의 Spring 바인딩·JVM 속성·환경 변수 읽기를 대조하고 `validate`, `plan`, `resolve`, 임시 사본의 `render`로 채널을 확인했다.

실제 업무 모노레포 적용 검증은 남아 있다.

2026-11-19에는 Gradle 모듈 경로 재매핑, IntelliJ에서 선택한 Spring 프로필, import 파일, 비활성 작업, 원격 기본 주소, 미확인 비밀값 공급이 있는 임시 모노레포로 절차를 수동 검증했다. 미확인 항목은 조사 기록에 남기고, 사용자 확인을 모의한 뒤 중앙 registry를 작성했다. 두 variant의 `validate`와 `plan`이 통과했고 PostgreSQL은 실제 variant의 계획에만 들어갔다. 메모리 설정 해석으로 접속점 주입을 확인했다. 비밀값을 공급하지 않은 CLI `resolve`는 변수 이름을 공개하지 않고 실패했다. 대상 소스의 파일 해시도 동일했다. 독립적인 스킬 실행과 실제 업무 모노레포 적용은 추가 검증이 필요하다.

## 4. 재개 지점

실제 등록에 연결할 때 T-100에서 변환 기능과 스킬을 함께 갱신한다. 현재 조사에 사용하려면 대상 모노레포와 앱·프로필을 지정하고 SKILL.md를 따른다.

T-140에서 검토된 실행용 registry를 AI가 직접 작성·수정할 관리 가이드를 추가했다. 자동 초안 변환 엔진은 여전히 T-100의 미구현 범위다.

다음 업무 모노레포 적용에서는 실행 후보 목록부터 작성하고, 우선 대상의 실제 실행 방식에서 발견되는 설정 출처와 도구가 지원하지 않는 입력을 확인한다.
