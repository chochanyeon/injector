# T-350 · Verify a fix with reproducible checkout evidence

**English** · [한국어](T-350.ko.md) · [Work index](../index.md)

## Design

Give an agent one command to start both checkouts, reproduce a checkout, and leave evidence that a reviewer can inspect. The shop fixture supplies fresh data. A reviewed scenario defines the initial state, expected response, and final state through read-only HTTP checks on Injector's selected graph. The existing Loki collector supplies correlated HTTP and Kafka evidence. This follows the evidence workflow described by Walden Yan. [AI Engineer CODE 2026 session](https://ai.engineer/code/2026/talks/walden-yan)

- A run with an unexpected initial state must leave evidence and skip the mutation.
- A confirmed failure of an expected result must fail the comparison, even when both checkouts fail in the same way.
- Fix verification must confirm a named failure on the baseline and require all candidate checks and required trace events to pass.
- A report must retain per-node startup progress and any available artifacts if execution stops early.
- Existing scenarios must continue to work.

## Development

1. Extend the trace scenario with `expect` and `stateChecks`. State checks call registered loopback HTTP endpoints with GET. A failed `before` check records the result and skips the scenario request. An `after` check can wait for an asynchronous effect. The recorder retains only selected values.
2. Add `--prove-fix CHECK_ID` to `compare-worktrees` and `compare-http`. A normal comparison requires two passing runs with equal observations. Fix verification requires the named check to fail on the baseline and the candidate to supply complete, passing evidence. Both modes use exits 0, 1, and 2 for `PASS`, `FAIL`, and `INCONCLUSIVE`.
3. Write `report.json` next to the recordings. It includes the scenario digest, checkout paths, node lifecycle events, and evidence. If a runner fails after the comparison starts, the report retains the failure and the completed side's recording.
4. Add a `mock` shop scenario that checks initial stock, order creation and amount, final stock, and Kafka-backed delivery. Its GET checks exercise the shop's PostgreSQL and Redis state through application endpoints.

## Verification

- The Windows trace and worktree tests verified that a wrong starting stock prevents checkout, a shared wrong result fails, a missing endpoint produces `INCONCLUSIVE`, and an app that exits before readiness leaves a report and the completed baseline recording.
- With Docker Desktop and the shop JVM services, equivalent checkouts passed all six checks and recorded ten HTTP and Kafka events. Changing the mock unit price from 999 to 998 produced HTTP `201` with an incorrect total of 1,996 cents in both the response and the stored order. Comparing the failing recording with itself returned `FAIL`. Comparing it with the corrected recording using `--prove-fix response` returned `PASS`.
- A live `compare-worktrees --prove-fix response` run started both copies in succession and wrote a `PASS` report with eleven ready nodes per run, two baseline failures, and six passing candidate checks.
- The Windows regression rerun passed 144 tests, including Spring Boot and WireMock Vault. Both opt-in shop tests passed during the initial run. The existing default-registry session test failed its process-ID check once during that run and passed in isolation and on the regression rerun. No Injector-managed Docker containers remained.

## Resume point

Use the [shop recipe](../../examples/demo/monorepo/README.md#verify-a-checkout-fix) on macOS and then a work monorepo. The next development item is to run several reviewed scenarios per fix. A fix can then prove its original failure and check related regressions in the same report.
