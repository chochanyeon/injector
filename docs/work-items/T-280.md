# T-280. Vault and log integration in the shop demo

**English** · [한국어](T-280.ko.md)

[Work index](../index.md) · Prerequisite T-270

## Design

Use WireMock to serve the demo's service-specific Vault KV v2 configuration. Run Loki on loopback and send structured application logs with a request ID carried through HTTP and Kafka.

Accept the work when both profiles start the new dependencies, the same Vault key produces distinct Redis TTLs, and one Loki query finds a checkout across HTTP services and the Kafka consumer.

## Development

- The demo Compose file, registry, and node files declare Vault and Loki and inject their host endpoints into the JVM launch environment. Each Vault path has its own WireMock fixture.
- The shared Java library reads Vault settings at startup, propagates request IDs across HTTP calls, and sends structured events to Loki. Orders also forwards the ID as a Kafka header so Notifications can log the same ID when it stores the delivery.
- The demo guide covers both ports, sample settings, and a checkout log query for macOS shells and PowerShell. Log delivery is asynchronous with a bounded number of in-flight requests, and logs live for the duration of the demo session.

## Verification

- Registry validation and checkout plans passed with 12 nodes in `real` and 11 in `mock`. Docker Compose listed both new services and the Loki image accepted the config.
- On Windows with Docker Desktop and JDK 25, `installDist` and the opted-in `test_shop_demo.py` covered checkout in both profiles, Vault access and rejection, service-specific Redis TTLs, and Loki lookup of the HTTP calls and Kafka delivery for the same request ID.
- The default Python suite passed 129 tests with seven opt-in tests skipped. The demo also has macOS shell instructions. The live run used Windows.
