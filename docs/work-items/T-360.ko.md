# T-360 · 수정 검증과 회귀 시나리오 함께 실행

**[English](T-360.md)** · 한국어 · [작업 인덱스](../index.ko.md)

## 설계

검토한 스위트 파일 하나에 대상 앱, 프로필, 시나리오 목록을 지정한다. 각 시나리오는 기존 워크트리 비교를 사용한다. 수정 검증과 회귀 검사를 함께 담을 수 있다. 첫 앱을 시작하기 전에 모든 시나리오를 검사한다.

- 시나리오와 워크트리마다 새 Injector 세션을 연다. 시나리오 검사로 초기 데이터 상태를 확인한다.
- 동작이 기대와 다르면 다음 검사를 계속한다. 기동이나 정리가 실패하면 다음 검사를 시작하지 않는다. 끝난 결과와 남은 항목을 보고서에 남긴다.
- 전체 판정, 판정별 건수, 세부 보고서 링크를 제공한다. 모든 항목이 통과해야 스위트가 통과한다.

## 개발

- `verify-suite`를 추가했다. 버전 1 스위트는 공통 [스키마](../../schemas/http-observation-v1.schema.json)로 검사한다. 이름이 다른 시나리오를 최대 16개까지 순서대로 실행한다.
- 항목마다 기존 [워크트리 실행기](../../injector_core/observation.py)를 사용한다. 중단 시 상세 보고서를 남기고 중단 종료 코드를 유지한다. [스위트 실행기](../../verifier/worktree_suite.py)는 `report.json`과 `summary.md`에 상대 경로로 증거를 연결한다.
- [체크아웃 스위트](../../examples/demo/monorepo/scenarios/checkout-fix-suite.json)를 추가했다. 두 번째 항목은 첫 항목의 주문 ID를 다시 사용해 상태 격리를 확인한다.

## 검증

- Windows Docker와 JVM에서 실제 쇼핑몰을 실행했다. 두 항목 모두 `PASS`였다. 첫 항목에서 기준 가격 오류를 재현했고 후보는 통과했다. 잘못된 수량 요청은 양쪽에서 HTTP `400`이었다. 후보의 초기·최종 재고는 모두 10개였고 주문과 배송 기록도 없었다.
- 로컬 프로세스 테스트에서 뒤에 있는 시나리오의 사전 검증, 동작 차이 발견 후 계속 실행, 각 세션의 카운터 초기화, 기동 실패와 중단 시 보고서 보존을 확인한다.
- Windows 회귀 테스트는 Spring Boot를 포함해 141개가 통과했다. 별도 실행 옵션이 필요한 Docker 테스트 7개는 건너뛰었다. 이 변경의 Docker 검증은 실제 쇼핑몰 스위트로 수행했다.

## 재개 지점

기대하는 이벤트의 누락과 예상치 못한 이벤트 발생을 직접 확인하는 검사를 추가한다. macOS와 업무 모노레포에서 스위트를 실행한다.
