# 모노레포 등록 프로토콜 v0.1

이 문서는 LLM과 사람이 앱 등록 정보를 조사·검토할 때 사용하는 산출물 계약이다. Injector 실행 엔진의 설정 스키마는 아니다. 자동 등록·주입·기동 기능을 추가할 때 실행용 스키마로 변환하는 단계가 필요하다.

## 입력과 조사 범위

입력은 모노레포 경로, 대상 앱(지정하지 않았다면 앱 후보 목록), 조사할 실행 프로필·모드다. 프로필이 지정되지 않았으면 발견한 선택지를 보고하고 구성별 정보를 섞지 않는다. 전체 저장소 등록 요청은 실행 앱 후보를 모두 목록화한 뒤 앱별로 조사한다.

우선 `rg --files`로 빌드 정의, Compose, Dockerfile, 실행 스크립트, IntelliJ 실행 구성, 애플리케이션 설정을 찾는다. 소스와 문서는 필요한 부분만 읽고 빌드 결과·의존 패키지·대형 데이터는 탐색에서 제외한다.

| 조사 대상 | 확인할 내용 |
|---|---|
| Maven·Gradle·기타 빌드 정의 | 모듈 구조, 실행 가능한 앱과 공통 라이브러리 구분 |
| 실행 스크립트·IDE 구성 | 진입점, 작업 디렉터리, VM 옵션, 환경변수, 프로필 |
| 앱 설정과 클라이언트 생성 코드 | 외부 호출 주소, DB·브로커 연결, 값의 참조·기본값 |
| Compose·Dockerfile | 서비스 이름, 내부·공개 포트, 실행 명령, healthcheck |
| 대역 설정 | WireMock 등 모의 대체 범위와 필요한 부가 의존성 |
| Vault 관련 설정·클라이언트 | 앱이 환경·파일만 읽는지 API를 직접 호출하는지, KV 버전·mount·경로·응답 키·추가 인증 요청 |
| 문서·샘플 환경 설정 | 의도와 추가 단서. 실제 실행 설정과 다르면 불일치 기록 |

JAR 라이브러리 참조만으로 앱 간 런타임 의존성을 만들지 않는다. 같은 호스트 이름을 사용한다는 이유만으로 서비스 동일성을 확정하지 않는다. Kafka처럼 앱이 공통 브로커를 사용한다면 브로커 의존성을 기록하고, 메시지 생산자·소비자의 기동 필요성은 별도 근거로 판단한다.

## 값과 근거의 처리

- 기존 값, LLM의 로컬 변경 제안, 미확인 값을 구분한다. 개발 서버 주소를 임의의 로컬 주소로 덮어쓰지 않는다.
- 환경변수 참조, 프로필별 덮어쓰기, 설정 서버에서 공급하는 값은 확인한 범위까지 추적한다. 코드가 없거나 비밀값이라 확인할 수 없는 것은 `null`과 질문으로 남긴다.
- 비밀번호·토큰·실제 자격증명을 산출물에 복사하지 않는다. 변수 이름과 필요한 비밀값 참조만 기록한다. 근거 코드 인용에도 비밀값을 포함하지 않는다.
- 근거 위치는 모노레포 기준 상대 경로와 줄 번호로 기록한다. `observed`는 파일이 직접 뒷받침하는 사실, `inferred`는 근거에서 추론한 관계다. `proposed`는 변경 제안으로 소스 사실처럼 취급하지 않는다.
- `local.test.com → 127.0.0.1`은 이름 해석 정의다. 바인딩 주소, 논리 호스트 이름, 컨테이너 서비스 이름, 컨테이너 내부 포트, 호스트 공개 포트와 구분한다. HTTP/HTTPS, 경로, TLS·인증 요건도 발견하면 기록한다.
- 준비 상태 확인 방법을 발견하지 못했으면 `null`로 둔다. 확인 없이 `/health`나 기본 포트를 만들어 넣지 않는다.

## 산출물

기본 산출물은 대상 모노레포의 `injector-onboarding/registration-draft.json`과 `injector-onboarding/findings.md`다. 사용자가 다른 출력 위치를 지정하면 따른다. 기존 파일은 먼저 읽고 변경 범위를 유지한다. 이 디렉터리를 Injector가 자동으로 읽는다는 의미는 아니다.

### JSON 구조

형식 예시는 `../assets/registration-draft.example.json`이다. 추가 정보를 위해 스키마를 임의로 늘리기보다 `findings`에 설명하고, 초안 계약 변경이 필요하면 그 이유를 기록한다.

| 필드 | 내용 |
|---|---|
| `draftVersion` | `0.1` |
| `status` | `draft`. 실행 가능 상태를 뜻하지 않음 |
| `scope` | 대상 앱 ID 목록과 프로필·모드. 미정이면 `null` |
| `nodes` | 앱·인프라·대역·외부 의존성의 등록 후보 |
| `nodes[].id` | 중복되지 않는 안정적인 ID |
| `nodes[].kind` | `application`, `infrastructure`, `mock`, `external` |
| `nodes[].repoPath` | 모노레포 내 앱 경로. 외부 자원은 `null` |
| `nodes[].execution` | `mode`, `workingDirectory`, `command` 인자 배열, `mainClass`, `vmOptions`, `environment`. 미확인 필드는 `null` |
| `nodes[].endpoints` | 이름 있는 접속점의 배열 |
| `endpoints[].id` | 노드 안에서 중복되지 않는 접속점 ID |
| `endpoints[].protocol` | 확인한 통신 프로토콜 |
| `endpoints[].bind` | 수신 주소 `host`, `port` |
| `endpoints[].addresses` | 호출자별 `from`, `host`, `port`, `scheme`, `path` |
| `nodes[].readiness` | 확인한 준비 기준. 없으면 `null` |
| `dependencies` | `from`, `to`, `endpoint`, `injections`를 가진 방향 간선 |
| `injections[]` | `channel` (`environment` 또는 `vmProperty`), `key`, `source` (대상 노드·접속점·호출 위치 참조) |
| `nameMappings` | `hostname`, `address`, `mechanism`. 설정 적용 지시가 아닌 조사 결과·제안 |
| `evidence` | `field` (JSON Pointer), `status`, `locations` (`path`, `line`), `note` |
| `findings` | 미확인·충돌·차단 사항의 `id`, `severity`, `field`, `message`, `question` |
| `startupOrder` | 선택한 그래프의 검토용 DFS 후위 순서. 확정 불가능하면 `null` |

명령은 사람이 검토할 인자 배열로 보관하며, 이 프로토콜이 실행 권한을 부여하지 않는다. `source`는 구조화한 참조이고 `${...}` 같은 실행 엔진의 치환 문법을 정의하지 않는다. 공통 설정과 프로필별 적용 결과를 보고서에서 구분한다.

비어 있는 배열은 해당 항목이 없음을 조사로 확인했을 때 사용한다. 아직 조사하지 않았거나 값이 미확인인 경우는 `null`로 두고 `findings`를 남긴다. 실행에 필요한 정보가 빠졌다는 이유로 추정값을 채우지 않는다.

### 조사 보고서

`findings.md`에는 조사 범위·제외 범위, 앱 목록과 식별 근거, 선택한 그래프, 기존 접속 정보와 로컬 변경 제안, 충돌·질문, 다음 적용 단계를 기록한다. 준비 상태·실행 방법이 미확인이면 그래프 순서를 계산할 수 있어도 현재 실행 가능한 환경으로 표현하지 않는다.

## 그래프 검토 규칙

1. 호출 앱에서 필요한 서비스로 간선을 그린다. 각 의존성의 전이적 의존성도 조사한다.
2. 프로필·실제 실행·모의 대체 선택을 반영한 그래프를 만든다. 대역을 선택하면 실제 앱 전용 의존성을 그대로 붙이지 않는다. 서로 다른 모드의 그래프는 분리한다.
3. 공통 자원은 같은 ID로 참조한다. 같은 ID에 상충하는 실행 정의·포트가 있으면 불일치로 남긴다.
4. 방문 중 노드를 다시 만나면 순환 경로를 보고한다. 순환·미해결 간선이 있으면 `startupOrder`를 확정하지 않는다.
5. 의존성 목록 순서대로 DFS 후위 순서를 계산하고 공통 노드는 한 번만 포함한다. 이 목록은 실행 계획 초안이며 실제 프로세스를 실행하지 않는다.

## 완료 확인

### Vault API를 로컬 대역으로 대체하는 경우

사용자가 실제 Vault 연동 대신 로컬 값 공급을 요청하면 실제 비밀값을 조회하지 않는다. API를 직접 호출하는 앱은 WireMock 등 HTTP 대역의 등록 후보로 모델링한다. 환경변수·파일만 읽는 앱은 해당 입력 위치의 로컬 설정 주입을 검토한다.

로컬 대역에서는 서비스 ID별 secret 경로와 응답 값을 분리한다. 기본 경로 규칙은 `/v1/<mount>/data/<service-id>`이며 같은 키라도 서비스별 값을 합치거나 다른 서비스의 값으로 대체하지 않는다. 실제 앱에서 조회 경로를 바꿀 설정 위치를 확인하고, 변경 가능 여부가 미확인이면 질문으로 남긴다. 이 규칙은 로컬 대역의 선택이며 모든 회사 Vault가 이 경로를 사용한다고 가정하지 않는다.

조사 보고서에 요청 메서드·경로·KV 버전·mount·필요한 헤더 이름, 응답 envelope·앱이 읽는 키, 주소를 바꿀 설정 키를 근거와 함께 기록한다. 사용자가 채울 로컬 값은 미확인 항목으로 남긴다. KV v2의 `data.data` 구조를 KV v1에 무조건 적용하지 않는다. login·token lookup·갱신·namespace·엔진 탐색 요청은 앱/SDK가 실제로 요구하는지 확인하고, 확인되지 않은 기능의 호환성을 주장하지 않는다.

지원하지 않는 API를 성공한 것처럼 반환하지 말고 미지원 범위를 보고한다. 로컬 더미 토큰과 실제 인증정보를 구분하며, 조사 산출물에는 회사 토큰·비밀번호를 복사하지 않는다. 이 사례의 상세 요청 계약은 보고서에 남기며 조사 JSON 계약의 필드를 임의로 늘리지 않는다.

### 일반 완료 기준

- JSON이 파싱되고 노드·접속점 ID가 중복되지 않으며 간선·주입 참조가 존재하는가?
- 실행에 영향을 주는 값과 간선마다 근거 또는 명시적인 변경 제안·미확인 기록이 있는가?
- 근거 파일과 줄을 실제로 확인했으며, 비밀값이 산출물에서 제외되었는가?
- 모드·프로필·호출자 위치가 섞이지 않았고 공유 의존성과 순환을 확인했는가?
- `startupOrder`의 모든 의존성이 해당 앱보다 앞에 있고, 미해결 관계가 있으면 순서가 `null`인가?
- hosts/DNS 변경, 설정 적용, 앱 실행을 이미 수행한 것으로 잘못 보고하지 않았는가?

질문은 미확인 대상 앱, 프로필, 의존성 식별, 포트·호스트 충돌처럼 실행 계획을 막는 항목부터 묶어서 제시한다. 답변과 무관하게 조사할 수 있는 앱은 계속 정리한다.
